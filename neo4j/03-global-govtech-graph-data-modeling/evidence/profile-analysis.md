# PROFILE Analysis Contract

The CI run captures actual Neo4j `PROFILE` output before and after the capability-domain refactor.

## Baseline

```cypher
PROFILE
MATCH (s:GovTechSystem)-[:ENABLES]->(c:Capability)
WHERE c.category = 'Digital Identity'
RETURN DISTINCT s.name AS system
ORDER BY system;
```

The baseline must inspect `Capability.category` during execution.

## Refactored

```cypher
PROFILE
MATCH (d:CapabilityDomain {name: 'Digital Identity'})
      <-[:IN_DOMAIN]-(c:Capability)
      <-[:ENABLES]-(s:GovTechSystem)
RETURN DISTINCT s.name AS system
ORDER BY system;
```

`CapabilityDomain.name` has a uniqueness constraint, so the refactored query has a canonical indexed anchor rather than depending on a repeated category property on every capability.

## Interpretation rule

This graph is intentionally tiny. Differences in rows, database hits, memory or operators are evidence about **query shape and search-space selection**, not a benchmark for enterprise-scale performance.

PoW #3 must not claim a production performance improvement merely because the refactored plan looks better on this instance. A scaled performance claim would require representative data volumes and workload testing.

## Runtime files

- `profile-before.txt` is generated by CI before refactoring.
- `profile-after.txt` is generated by CI after refactoring.

These runtime files are uploaded as workflow evidence and should be summarized after the first verified CI run.
